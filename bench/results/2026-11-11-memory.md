# Memory: where 1.1-1.7 GB goes (2026-11-11)

The high RSS of sculpture-forest, night-city, tenna-dance and yingyang-kitty is a **load-time peak, not steady state**.
`VmHWM` vs `VmRSS` 20 s after start (1080p, release): sculpture-forest 1.69 GB -> 333 MB, night-city 1.23 GB -> 359 MB,
yingyang-kitty 1.07 GB -> 306 MB (steady: ~80 MB anonymous, ~200 MB file-backed libraries, ~55 MB shared).

Breakdown of the peak (smaps at the highest sampled RSS, sculpture-forest, 1.53 GB): 486 MB `nvidiactl` mappings
(NVIDIA pinned host-visible memory: the upload staging blocks), 378 MB anonymous (decoded texture buffers; the texture
memory backend's own count peaks at 731 MB over 613 allocations, all live at once), 40 MB libLLVM (shader compiler).

Why: the scene parser decodes every texture into one `Image` before the resource plan runs; the plan holds all of them
until it completes, while uploads stage a second copy in pinned memory (3 batches in flight, bounded by count, not
bytes; `PrepareImage` itself does not copy, uploads reference the image). Everything is freed once the plan completes.

Tried: flush the pending uploads at 64 MB instead of after four contents (vrento `RegistryTextureContext::MakeRoom`).
Max RSS over 4 runs: sculpture-forest 1319-1651 -> 1279-1332 MB, night-city 1118-1566 -> 1080-1351 MB, yingyang-kitty
unchanged (1040). 5-15 % on a noisy peak, so not kept.

What would cut the peak for real (not done; a loader redesign): decode on demand when the plan reaches a texture and drop
the `Arc<Image>` the plan holds right after its upload is recorded, so a texture is resident decoded for the length of
its own upload instead of the whole load. Expected peak: the largest few textures plus staging (~200-300 MB) instead of
the sum of all. Risk: device-lost or resolution-change rebuilds re-upload from the retained `Image`, so those would have to
re-decode. Steady state needs nothing (the 300-360 MB floor is libraries and driver state).

## Byte-based upload windows (vrento `perf-upload-bytes`)

The count windows (4 pending contents, 3 batches in flight) admitted any number of bytes. Pending pixels now flush at 64 MB and
a batch waits while 128 MB are in flight. Measured (max RSS over 4 runs, 1080p, load to frame 30): sculpture-forest 1323-1673 ->
1183-1233 MB, night-city 1204 -> 1079 MB, yingyang-kitty unchanged 1040. Pinned staging at the peak: 486 -> 180 MB. The
decoded-pixel peak is unchanged (730 -> 782 MB, ~39 live mappings): up to four decodes run at once plus their finished
results, so with 4k textures that is 8 images of ~100 MB. Bounding that needs the decode scheduler to know each texture's
size (a size query on the loader trait, then admit decodes by bytes): the next step, not done.

## Size-aware decode scheduling (vrento `perf-decode-budget`)

Serialising the decodes (1 MB budget) showed concurrency is the decoded-pixel peak: sculpture-forest 1.2 GB -> 776 MB. The
loader now reports each texture's decoded size from its header and a `DecodeBudget` admits decodes while the estimated bytes in
flight fit (one always runs; `VRENTO_DECODE_BUDGET_MB`, default 128). Sweep, 3 runs each (max RSS / peak live decoded bytes / load):

| budget | sculpture-forest | night-city | yingyang-kitty |
|---|---|---|---|
| none (1024) | 1250 MB / 746 / 2.3 s | 1278 / 469 / 1.8 s | 1038 / 251 / 1.2 s |
| 256 MB | 920-956 / 406-465 / 2.4 s | 1171 / 362 / 1.9 s | 1038 / 251 / 1.2 s |
| 128 MB (default) | 760 / 290 / 3.1 s | 1171 / 362 / 1.9 s | 1038 / 251 / 1.2 s |
| 64 MB | 765 / 249 / 3.1 s | 1171 / 362 / 1.9 s | 1038 / 251 / 1.2 s |

night-city and yingyang-kitty are bounded by single large textures (362 and 251 MB live): the decoded image, an equally large
pinned staging block, and ~330 MB of libraries and driver state. Cutting those needs strip-wise decode and upload (decode a band
of rows, stage it, free it), which the decoders do not support yet.
